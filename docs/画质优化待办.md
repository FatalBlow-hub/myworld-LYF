## 背景与结论

**结论：不换技术栈。** Three.js 在画质方向是优势而非瓶颈——`MeshStandardMaterial`、
`shadowMap`、`EffectComposer`、`Reflector`、`SSAOPass` 全是内置的。换 Babylon.js
没有本质区别，换 WebGPU 的收益在 compute 加速网格化、和画质无关。

当前画质不"真实"的 5 个原因：

| # | 原因 | 定位（按符号，不按行号） |
| --- | --- | --- |
| 1 | 贴图 16×16 + `NearestFilter`，硬边马赛克 | `src/render/Textures.ts` → `createAtlas()` 里 `texture.magFilter` / `minFilter` 两行 |
| 2 | 材质是 `MeshLambertMaterial`，无法线/粗糙度/金属度 | `src/render/ChunkMeshCache.ts` → `opaqueMat` / `waterMat` 构造处 |
| 3 | 从未启用 `shadowMap`，画面"平" | `src/render/Renderer.ts` 构造函数（全局搜不到 `shadowMap` 调用） |
| 4 | 水被烘进 chunk 静态网格，完全没有动画 | `src/render/ChunkMesher.ts` → `meshChunk()` 里 `alphaBlend` 把水推进 `water` 几何数组 |
| 5 | 花是两张固定 45° 交叉片，无随机、无风摆 | `src/render/ChunkMesher.ts` → `emitCross()` |

> ⚠️ 本文档定位一律用**符号名**（函数 / 变量 / 构造处），不写行号 —— `src/` 正处于并行改动中，行号必然失效。

**与性能优化的关系**：当前瓶颈在 CPU 网格化；加了阴影/反射/后处理之后，
瓶颈会转移到 GPU 填充率。所以画质优化**必须在性能优化之后**做——顺序对了。

## 阶段一：低风险高回报

全部是纯渲染层改动，**不动任何美术资产**，可独立测试、可单独回滚。

### T1 水面动起来（优先，最高性价比）

- **现状**：水在 `meshChunk` 里和方块一起烘成静态 `BufferGeometry`，
  一丁点动画都没有；材质只有 `transparent` + `depthWrite:false`
- **做法**：给 `waterMat` 挂 `onBeforeCompile` 注入着色器
  - 顶点着色器：按世界坐标 `xz` + `uTime` 叠 2–3 个正弦波做起伏，振幅约 0.03 格
  - 片段着色器：两层不同速度滚动的法线扰动 → 波纹高光
  - 保留 `transparent` + `depthWrite:false`，不动现有透明排序
- **涉及文件**：`src/render/ChunkMeshCache.ts`（`waterMat` 构造处 —— 重构后三个材质都在这里，不再是 `Game.ts`）、
  可新建 `src/render/WaterMaterial.ts` 封装
- **收益**：水从"一块蓝板"变成"会动的水"，视觉提升最大
- **风险**：低。但要在 `Renderer` 里统一提供 `uTime` 并每帧更新

### T2 环境光遮蔽 AO

- **现状**：方块交界处没有明暗过渡，大平面看着"薄"
- **做法**：在 `pushQuad` 里按每个顶点周围 3 个邻居方块算 AO 权重，
  写入顶点色属性；材质开 `vertexColors: true`
- **涉及文件**：`src/render/ChunkMesher.ts`（`pushQuad` / `GeoArrays` / `toGeometry`）、
  `src/render/ChunkMeshCache.ts`（给三个材质开 `vertexColors: true` 改这里，不在 `Game.ts`）
- **收益**：立体感质变，voxel 游戏的核心观感来源
- **风险**：中。顶点顺序影响 AO 采样，需要逐面核对；花草/异形方块要单独处理

### T3 花朵风摆与随机化

- **现状**：`emitCross` 写死两张 45° 斜面薄片，所有花长得一模一样
- **做法**（三项可拆）：
  1. 每朵花随机旋转角 + 随机高度（0.8–1.0 格），用坐标哈希保证位置固定
  2. 顶点着色器按 `uTime` + 顶点高度做摆动，越靠上摆幅越大
  3. 花瓣用 2–3 层薄片错开，不再是两片
- **涉及文件**：`src/render/ChunkMesher.ts`（`emitCross`）
- **协作**：⚠️ **T3 必须早于小岛生存 A7（南瓜/西瓜作物）**。本项会把 `emitCross` 改造成
  「随机旋转 + 随机高度 + 风摆」的通用件；若 A7 的苗期方块先做，贴图完成后还要回头
  适配风摆 → 返工。详见「与小岛生存开发的协作约定」
- **收益**：花草"活"过来；顺带让草丛、水稻也受益
- **风险**：低。依赖 T1 建立的 `uTime` uniform 机制

## 阶段二：需配合架构改动

### T4 阳光阴影

- **现状**：无阴影，画面缺乏空间层次
- **前置**：区块网格现在是 16×64×16 整根柱子，包围盒巨大 →
  shadow camera 很难配准，且白白多一遍 draw call。
  **必须先有「区块按高度分段 / 子区块 16³」**
  - 如果当前这轮优化已含子区块拆分 → 直接开工
  - 否则先补这一项，在本文档标为 `T4-pre`
- **做法**：`renderer.shadowMap.enabled = true` + `PCFSoftShadowMap`；
  `sun.castShadow = true`；正交 shadow camera 覆盖玩家周围约 64 格并跟随玩家；
  区块网格 `castShadow` / `receiveShadow` 全开
- **涉及文件**：`src/render/Renderer.ts`、`src/render/ChunkMeshCache.ts`（网格的 `castShadow`/`receiveShadow`；子区块拆分后缓存 key 不再是一个 `cx,cz` 一个网格，释放逻辑要跟着改）、`src/render/ChunkMesher.ts`
- **收益**：画面层次感最大来源
- **风险**：中。性能翻倍消耗，必须配质量档位

### T5 天空与雾

- **现状**：纯色 `scene.background` + 线性 `THREE.Fog(0x87ceeb, 40, 90)`
- **做法**：反面渲染的大球 + 顶点色渐变着色器，随昼夜变色；雾改 `FogExp2`
- **涉及文件**：`src/render/Renderer.ts`（`setDaylight`）
- **收益**：天空与远景观感提升明显
- **风险**：低。但要和 `setDaylight` 的颜色插值逻辑对齐

## 与小岛生存开发的协作约定

另一条并行线是 `docs/小岛生存-需求评估与开发文档.md`（A 组小岛生存玩法 + B 组大厅联机）。
两条线**内容上不冲突**（渲染层 vs 玩法/网络层），但共享文件与性能预算。

### 落点分离（2026-10-15 核对）

| 文件 | 画质线 | 小岛线 | 冲突 |
| --- | --- | --- | --- |
| `src/render/ChunkMeshCache.ts` | T1 材质、T2 `vertexColors`、T4 `castShadow` | — | 无 |
| `src/render/Renderer.ts` | T4 阴影、T5 天空与雾 | — | 无 |
| `src/render/ChunkMesher.ts` | T2 `pushQuad`、T3 `emitCross` | A7 新作物苗期走 `emitCross` | **有** |
| `src/config.ts` | 阴影/水体/雾参数 | A2 `KEYS`、A4 `EAT_HP` | 弱（同文件不同区段） |
| `src/ui/Hud.ts` | — | A3 饥饿条 | 无 |

> 此前判断的 `Game.ts` 冲突**已解除**：三个区块材质已从 `Game.ts` 抽到
> `ChunkMeshCache.ts`，`Game.ts` 现 454 行，留给小岛 B 组的场景切换与网络接入。

### 三条硬性约定

1. **T3 必须早于小岛 A7。** 否则 A7 的作物贴图完成后还要回头适配风摆 → 返工。
2. **动 `src/config.ts` 前先同步。** 两条线都会改它（现 284 行），改前互相说一声，避免合并冲突。
3. **不要并行改 `ChunkMeshCache.ts` 的材质构造。** 它是 T1/T2/T4 的共同落点，合并代价高。

### 执行顺序（性能预算是硬约束）

画质每一项都在**加 GPU 负担**；小岛 B 组联机则会让区块重建更频繁（方块改动要广播）。
两条线同时压上来会互相放大，所以整体顺序：

```
① 当前这轮性能优化（含子区块拆分）  ← 腾出性能预算
② 小岛 A 组 + M0 联机骨架           ← 单向长链路，不宜被打断
③ 画质 T1 / T2 / T3                 ← 独立可验证、可回滚
④ 画质 T4（依赖①的子区块）+ T5
⑤ 画质阶段三 后处理                 ← 最后，且必须配质量档位
```

画质整体后移的原因：每一项都能独立验证、独立回滚；而联机 M0→M6 是严格单向依赖的
长链路，中途被画质改动打断代价大。
