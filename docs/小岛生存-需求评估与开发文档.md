## 二、总体结论

**A 组（小岛生存玩法）：合理，且大部分能复用现有机制，建议先做。**
现有代码里已经有：作物生长表 `CROP_NEXT`、播种 `plantSeed`/`plantCarrot`、食物效果表 `EAT_HP`（`config.ts:82`）、速度加成 `BOOST`（腌菜桶用的 `speedBoostT`）、地形群系与概率生成（`TerrainGen.ts` 的 `hash()` + `ORE.*_CHANCE`）。A 组是"加内容"，不是"改架构"。

**B 组（大厅与联机）：想法合理，但这是从「单机 + 云存档」升级为「多人在线」，是架构级改造，不是加功能。**
当前服务端 `server/index.mjs` 只有 HTTP REST（注册/登录/存档上传下载），**没有任何实时通信**；客户端世界是**纯本地权威**（挖/放方块全在浏览器里算，服务端不校验）。要做 B 组必须先补三样东西：实时通道、场景（大厅/岛屿）切换、服务端（或房主）权威校验。

**最大的一条债**：B9/B10 的挖掘权限在现在这个架构下**无法真正生效** —— 因为挖不挖得动完全由浏览器说了算，访客改前端就能挖。必须先把"谁有权改世界"这个问题解决（服务端权威或房主权威），否则权限只是个装饰。

**建议顺序**：先做 A 组（能立刻玩到、验证玩法是否有趣），同步做 B 组的前置改造（M0），最后做排队/匹配/访客流程。

### B9/B10 的两个硬问题

1. **权限形同虚设**：现在挖/放是 `PlayerActions.updateMining/placeItem` 在浏览器里直接改 `World`。要真正拦住访客，必须把"能不能挖这个方块"的判定放到**房主端或服务端**（服务端权威最干净，但要把世界改动同步上云，改动量很大；房主权威折中：访客的挖掘请求发给房主，房主校验后广播结果）。
2. **规则自相矛盾**：B9 说"三选一（基础选项）"，B10 却说"同时勾选①和③" —— 单选怎么同时勾选？需要需求方澄清：是「单选 + 一个反转开关」，还是「多选组合」？

## 六、工作量与风险总评

| 项 | 估算 |
| --- | --- |
| A 组（小岛生存玩法） | ≈ 6 人天 |
| B 组（大厅与联机） | ≈ 15-25 人天 |

**风险清单（按严重度）**

1. **权限无法真正生效**（高）：不解决权威问题，B9/B10 就是摆设 → M5 必须做，不能跳过。
2. **WebSocket 部署卡在运维**（中高）：Nginx 需要 `Upgrade` / `Connection` 头支持 ws 反代，且可能要开新端口；项目约定里"证书/防火墙别碰"，需要走管理员。
3. **存档模型冲突**（中）：现在是「一个账号一整档 JSON」；岛屿 + 大厅意味着一个账号可能有多座岛/多个场景 → 存档结构要扩（好消息：阶段 5 已加 `SAVE_VERSION` 与 `migrateSave()`，可平滑升级）。
4. **世界同步的性能**（中）：多人同岛时方块改动要广播，区块网格重建频繁 → 建议 M6 阶段做，先保证 M3-M5 的"访客进岛"是房主权威 + 增量同步。
5. **需求本身有矛盾点**（低但阻塞）：见第七节，动工前必须澄清，否则返工。

## 七、规则决策（2026-10-15 已拍板，可直接开工）

需求方授权由我方按"最小歧义 + 最贴近原意 + 实现成本最低"原则拍板，结论如下。**后续如与原意不符，改的是这一节，不是代码。**

### 规则层面

| # | 问题 | 决策 | 理由 |
| --- | --- | --- | --- |
| 1 | B9/B10 权限到底单选还是多选 | **拆成两个控件**：①模式三选一（全禁 / 全允许 / 仅允许清单）②「水果例外」开关。例外开关只在「全禁」和「全允许」下生效：全禁+例外 = 只有水果不能挖；全允许+例外 = 只有水果能挖 | 原描述"同时勾选两个单选"自相矛盾；拆开后既保留了「反转」的效果，又是可实现的确定逻辑 |
| 2 | B8「开过创造模式」的判定 | **存档级**：`SaveData.everCreative`，本档只要选过/切过创造模式就置 true，双方都要为 false 才验证通过 | 现有是"一个账号一档"，存档级等价账号级且语义更准（防的是这档作弊）；实现最省 |
| 3 | B4 背包与铁锭 | **随身背包（快捷栏+储物+装备）跨场景携带，岛屿世界独立存档**。2 铁锭从随身背包扣；离开岛屿时随身物品带走、岛屿改动留在岛上 | 有收益也有成本，且不破坏现有"一档"存档模型（只需把一档扩成主档+岛屿档） |
| 4 | A2 饥饿开关作用域 | **每档独立**，随存档保存；关闭时**暂停消耗、保留当前值**（不回满） | 开关是难度选项而不是重置按钮，保留值更符合直觉 |
| 5 | A5 饿死后重生 | 重生时饥饿**回满 7 格**（与血量一致） | 与现有 `Health.respawn()` 语义一致 |
| 6 | A6 转化在哪操作 | **背包 2×2 合成格与工作台都能用**，无需工具；N 个换 3N 个 | 复用现有 `RECIPES`/`UNCRAFT`，不加新 UI |
| 7 | A7 生长速度 | **每 60 秒长一级**（与现有水稻同节奏），种子→小苗→大苗→结果共约 180 秒；种在草地/泥土，不要求光照与水 | 复用 `CROP_NEXT` 与 `plantCarrot` 的现有规则 |
| 8 | A10 水果怎么掉 | **挖掉树叶时**判定 1%，不受工具影响 | 与现有 `dropOf()` 一致，只需扩展成概率掉落 |
| 9 | A9 一人几座岛 | **一个账号一座固定岛**，建新档时随机一种并记 `islandType`；去别人岛只是访问，不改变自己的岛 | 与"一账号一档"现状吻合 |
| 10 | B6 陌生岛的收获 | **临时副本**：岛上无怪无动物无沙漠雪地；可采集，随身背包能带走，离开后岛屿销毁 | 花 2 铁锭要有回报；副本销毁避免服务器无限堆积世界 |
| 11 | B2 大厅能不能走动 | **大厅内可自由走动（小房间，出不去），排队是独立逻辑队列**：进大厅即入队，轮到队首自动弹窗 | "完全锁死"体验很差；队列与移动解耦也更好实现 |
| 12 | B7 对方不在线 | **必须在线**，不在线直接提示"对方不在线"，不做离线留言 | 一期不做留言系统，避免额外状态机 |
| 13 | B13 同时几人 | **先按 2-4 人（房主权威）设计**，`net/` 层预留服务端权威接口 | 房主权威改动最小；真要 10+ 人再上服务端权威 |

## 八、交给 auggie 的提示词切分

评估通过后，按 M0→M6 每期一个提示词文件，建议落 `docs/_prompts/M0-联机骨架.md` … `M6-打磨.md`，每个提示词必须写清：

- 目标与验收标准（对应上表"验收"列）
- 允许改的文件范围（例如 M1 只允许 `src/player/Hunger.ts`、`src/ui/Hud.ts`、`src/config.ts`、`src/core/Survival.ts`）
- 禁止事项：不改 `docs/` 里已确认的规则、不动 `server/data.db` 里的真实存档、不引入新依赖（除 M0 的 `ws`）
- 完成后必须 `npm run build` 通过，并说明手工冒烟步骤

命令模板（工作区换成 `e:/myworld`，模型沿用你既定的 `gpt6.1-sol`）：

```bash
auggie -if <提示词路径> -m gpt6.1-sol --print -w e:/myworld --max-turns N --quiet
```

第一期（M0）建议加 `-a` 先做只读调研（确认现有服务端结构与部署约束），再放开写文件。
