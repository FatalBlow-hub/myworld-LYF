## 背景与目标

**现状（胖客户端 + 瘦服务器）**：地形生成、物理、怪物 AI、背包、合成、渲染全部在浏览器里跑（编译进那一个 JS 包）。服务器只提供：登录（`/api/auth/*`）、存/取存档（`/api/save`，存客户端交上来的 JSON）、联机中转（`WS /ws`：在线名单/大厅排队/访岛票据）、发静态包。**服务器不渲染、不模拟世界、校验不了规则**（存档只查版本号 `body.v`，库存/血量/坐标一律不验）。

**目标（服务端权威）**：服务器持有每个房间的权威世界状态（方块 + 怪物 + 掉落），负责跑怪物 AI 与世界周期、仲裁冲突；客户端退化成"渲染画面 + 发操作（移动/挖/放/拾取）"。渲染永远在客户端，变的是"世界状态以谁为准"。

```
现在：客户端 算+画 everything，服务器 只存 JSON + 转发
co-op：服务器 算这个世界（权威），客户端 只画 + 发操作
```

## 已定设计决策

| # | 决策 | 说明 |
| --- | --- | --- |
| 1 | 服务端权威房间世界 | 服务器内存持有活跃房间的方块/怪物/掉落状态 |
| 2 | 方块冲突服务端仲裁 | 所有挖/放过服务端校验，按接收顺序**后写覆盖**；v1 不做客户端预测 |
| 3 | 掉落"谁先捡到归谁" | 房间内掉落不挂个人名下，服务端按拾取请求到达顺序先到先得 |
| 4 | 怪物/场景要同步 | 服务端跑怪物 AI + 广播（不是各见各的） |
| 5 | 背包/血量各带各的 | 不共享个人背包与血量 |
| 6 | 移动=客户端算、服务端转发 | 省服务端 CPU（服务端不跑玩家物理，只转发位置） |
| 7 | 房间规模 2-4 人 | MVP 上限 |
| 8 | 空房卸载 | 最后一人离开 → 落库 + 从内存删除，只在有人在线时持有 |
| 9 | tick 预算 + 每房怪数上限 | 防 node 单线程被一个重房拖垮 |
| 10 | 并发房数上限先 8-12 | 合租机，别挤爆其它服务 |

## 资源评估（实测）

机器：腾讯云 4 核 / 3.65 G 内存（空闲 1.89 G）/ 负载 1.48，**合租**（还跑 sports、casino 等）。

| 项 | 现状 | 权威化后（每活跃房） |
| --- | --- | --- |
| 游戏进程内存 | 44 MB | +1-4 MB（大头=岛方块，每格 1 字节） |
| 游戏进程 CPU | ≈ 0% | 几个百分点／一个核（怪物 AI + 世界周期 + 转发；渲染不在服务端，零 GPU） |
| 网络 | 极低 | 每玩家几 KB/s（10 次/s 位置 + 偶发挖放） |

- **内存不是瓶颈**：50 房 ≈ 200-300 MB，机器扛得住。
- **CPU 是瓶颈但余量足**：游戏服务是独立进程、单 node 线程 ≈ 独占 1 核；每房约几个百分点 → 约 15-30 房吃满一核；**舒适区 8-16 房**。

## 关键风险与对策

1. **node 单线程**：一个重房卡顿会拖累同进程所有房 → tick 预算 + 每房怪数上限 + （必要时）worker/多进程。
2. **世界太大**：空房必须卸载（落库、释放内存），只在有人在线时持有。
3. **合租机**：给并发房设上限 + 监控，别挤爆其它服务。
4. **远程角色渲染**：从"只看自己"到"看队友"，需角色模型 + 插值，是"有没有在一起的感觉"的关键，别排到最后才发现。
