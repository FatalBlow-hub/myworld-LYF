| 项目 | 数据 |

## 二、总体结论

架构**文档写得好、代码跑在文档前面**。分层铁律基本守住（`src/world/` 零处反向依赖），但文档未覆盖的新层 `entities/`、以及 `core/` 里长出来的第二个上帝对象，已经成为扩展瓶颈。

一句话：**现在补框架的成本，远低于再堆 3 个玩法之后再补。**

## 四、问题清单（按优先级）

### P0 — 阻断扩展，必须先修

**P0-1 `core/Actions.ts`（470 行）是第二个上帝对象，且放错了层**

- 承担 10 类职责：挖矿进度、放置分发、快捷栏、掉落拾取、吃喝/药水、面板按键、M 键用方块、战斗、驯羊、床重生点、卡墙自救、撒货
- 直接 import 4 个 UI 面板（`Actions.ts:20-25`），`core` 层直接操作 UI 细节
- 依赖注入 18 项、其中 8 个是回调（`Actions.ts:35-64`）
- **整改**：挖/放置 → `core/PlayerActions.ts`；拾取 → `core/Pickup.ts`；吃喝/重生点 → `core/Survival.ts`；战斗 → `MobCombat`；面板按键 → `Panel.handleKeys()`；`Game` 瘦身为纯装配 + 调度
- **为什么没下沉到 interact/entities**：这三个模块都要开 UI 面板（开工作台、开染色台、弹提示），而下层依赖 `ui` 会破坏依赖铁律。真正的下沉要等 P2-1 把"提示/面板"从业务里解耦之后再做完

**P0-2 没有面板管理器**

- 面板互斥门禁是 `Game.tick` 里 5 段顺序 `if-return`（`Game.ts:413-446`）
- 每个面板的键盘处理各自一份：`Actions.panelKeys`（304）、`containerKeys`（318）、`Game` 里还有 dye/book 各一段
- **后果**：新增一个面板要改 3 处，且互斥关系靠代码顺序隐式保证
- **整改**：`ui/PanelStack.ts` — 面板栈 + 统一键盘路由 + 自动暂停

**P0-3 三套核心逻辑各复制多份，没有统一入口**

| 逻辑 | 复制点 | 份数 |
| --- | --- | --- |
| 掉落物生成 | `Game.ts:343-347`、`Actions.ts:451-467`、`DropHelpers.ts:17`、`Save.ts:292` | 4 |
| 伤害结算 | `Health` 内部、`Game.ts:113`、`Actions.ts:280`、`Tank.ts:101` | 4 |
| 射线/AABB 命中 | 核心实现只有 `Animal.ts:293` 的 `rayHitBox` 一份，其余是薄封装（✅ 已抽到 `entities/hitbox.ts`，Zombie/Tank 不再反向依赖 Animal） | 1（误判，已澄清） |

- **整改**：抽 `entities/spawnDrop()`、`player/damage()`、`interact/raycast()` 三个单一入口，其余改为调用

**P0-4 全局可变方块注册表 + 隐式初始化顺序**

- `GoldenRegistry.ts:35-46` 在运行时 push 改写 `BLOCKS / ALL_ITEMS / DYE_IDS / POTION_IDS / WAISTBAG_IDS`
- 副作用：`main.ts` 必须先于 `Game.ts:48` 的 `createAtlas()` 完成注册，顺序错了静默黑块
- **整改**：注册表构建期一次性冻结（`Object.freeze`），黄金系列改为同一张表里的普通条目

**P0-5 存档没有版本号**

- `Save.ts` 全文无 `version` 字段（与 `PROJECT_CONTEXT.md` 声称的"存档格式 v1"不符）
- `SaveData` 靠手工列举，`buildSave`（191）/ `applySave`（243）逐个系统手写
- **后果**：加任何新系统要改两处；老档读新格式会静默出错 —— 线上已有真实账号存档，风险最高
- **整改**：`SaveData.version` + 各系统自注册 serialize/deserialize

### P2 — 结构债，择机清理

- **P2-1** `entities/` 是文档外的新层且方向倒挂：`Potions.ts:10-13` 引 `ui/Hud` + `player/*` + `interact/BlockPicker`；`Animal.ts:9`、`ItemDrop.ts:7` 引 `player/Physics`。→ 文档补层；下层能力上提为纯函数
- **P2-2** `render/` 11 个纹理文件三种组织写法（`Record` 常量 / `addMetalPainters()` 函数式 / 行内现写）；`Painter` 类型定义在聚合器 `Textures.ts:15` 导致 5 个文件 type-only 反向引用。→ 抽 `render/painter.ts` 放类型
- **P2-3** 联机无落脚点：`Game` 硬编码单人单例（`this.controller`/`this.body`/`this.drops`），输入直读 `Controller`。→ 若要做多人，先抽 `Player` 抽象与网络层

## 五、整改路线图

每阶段独立可编译、可回滚，验收标准统一为：`npm run build` 通过 + 手动冒烟（开局 → 挖/放 → 存读档 → 打怪 → 开箱子）。

| 阶段 | 内容 | 涉及编号 | 风险 |
| --- | --- | --- | --- |
| 阶段 0 | 建立验证基线：`npm install` + `npm run build` 通过；补 `tsconfig` 严格度（如需要） | — | 无 |
| 阶段 1 | 抽统一入口：`spawnDrop()`（4 处 → 1）/ `damagePlayer()`（2 处 → 1）/ `rayHitBox` 归位 `entities/hitbox.ts` | P0-3 | 低（纯搬移 + 改调用点） ✅ 已完成 |
| 阶段 2 | 面板管理器 `ui/PanelStack.ts`，删掉 tick 里 5 段门禁 | P0-2 | 中（改交互路径） ✅ 已完成 |
| 阶段 3 | 拆 `Actions.ts` → `PlayerActions` / `Pickup` / `Survival` / `Menus` / `ChunkMeshCache`，`Game` 瘦身 | P0-1、P1-1 | 中 ✅ 已完成（`Game.ts` 527 → 454 行） |
| 阶段 4 | 方块表拆分（`Block.ts` 662 → 46）+ 黄金注册表冻结（删 `GoldenRegistry.ts`） | P0-4、P1-3 | 中 ✅ 已完成（谓词 tag 化 P1-4 未做） |
| 阶段 5 | 存档版本：`SAVE_VERSION` + `isSupportedSave()` + `migrateSave()` + 服务端同步 | P0-5 | 中 ✅ 已完成 |
| 阶段 6 | 玩法注册表化（怪物表 / 物品使用处理器表 / 形状表） | P1-2、P1-5 | 中 |
| 阶段 7 | 文档层补齐（`entities` 入档）、纹理文件统一、联机抽象预留 | P2 | 低 |

**顺序原则**：先统一入口（阶段 1），因为阶段 2/3/4 都会反复用到掉落与伤害入口；存档版本号（阶段 5）必须配合线上存档兼容性验证，不能与阶段 4 合并提交。

## 六、风险与约束

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 无自动化测试 | 仓库无 test 脚本、无测试用例 | 每阶段以 `npm run build` + 手工冒烟为关卡；建议阶段 0 起补最小冒烟清单 |
| 线上有真实存档 | 腾讯云 `49.235.124.163`，`server/data.db` 不随 rsync 覆盖 | 阶段 5 改动必须向后兼容老档，先本地造老档验证再上云 |
| 无 `node_modules` | 当前工作区刚克隆，依赖未安装 | 阶段 0 先 `npm install` |
| 单人开发、无 CI | 编译错误只能本地发现 | 每次改动后立刻 `npm run build`，禁止批量改完再编译 |
